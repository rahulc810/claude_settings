# Forge assessment — 2026-08-31 (revision mode)

Two revisions, no new skills. Triggered by the question: "handoff/resume are built for
cross-device sessions — do we need a local-continuation equivalent?" Evidence trail:
`docs/notice.md` 2026-08-30 `/observer` line — `/clear` typed 157× vs `/handoff` 5×,
`/resume` 1×.

---

## Revision 1 — handoff / resume gain a lightweight no-arg local-continuation path

**Modeled change.** `handoff` no-arg = quick local checkpoint (brief-mcp is a local
server, so handoff → `/clear` → `/resume` is already the same-machine path); `/notice`
pre-step drops from gate to suggestion; if a brief for the thread exists, `edit_brief`
it to current state instead of stacking a new `send_brief`. `resume` no-arg skips the
`search_all` sweep and shortlist entirely — `get_brief` the latest, confirm, continue.

**Proposer.** The 157–5 split is the whole case: the compact→store→restore loop exists
for exactly the `/clear` boundary and is routed around 97% of the time. Cause is
ceremony mismatch, not a missing capability — `resume`'s sweep + 5–7-row shortlist +
stop-and-ask is pure overhead when you just want your place back, and `handoff`'s
`/notice` gate adds a second skill invocation to a "save my place" action. The store
already supports latest-state (`edit_brief` / `rewind_thread`); the skill just never
told anyone to use it on re-handoff.

**Skeptic.**
- *Overlap* — a separate `handoff-local` / `resume-local` pair would share ~all of the
  compaction discipline with the originals (constitution consolidation signal,
  Distinctness ~2). Correctly avoided: this is a no-arg branch inside the existing
  skills, not new skills.
- *Realness* — recurring: one `/clear` per session, 157 in the window.
- *Skill-fit* — n/a, no new skill; the change is a procedure edit.
- *Context cost* — zero; no new `description` line.
- Residual risk: `resume` no-arg previously "skip to step 2" (which *was* the sweep) —
  the edit removes that contradiction, so behavior is now what the docs implied.

**Verdict.** Apply as a revision to both skills. **Applied.**

**Rating** (of the change): Recurrence 5 · Distinctness 4 (no neighbour does
local-cheap continuation) · Skill-fit 4 · Scope tightness 4 (one crisp trigger: no
argument) · Context cost 5.

## Revision 2 — forge covers targeted revision of an existing skill

**Modeled change.** New "revision mode": a prose argument naming a change to what an
existing skill *does* (procedure / triggers / tools / a `/notice` mis-calibration) is
in scope — skip the `docs/skill-ideas/` scan, run the Proposer/Skeptic passes on *the
change*, write the report, apply the `Edit`, no idea file to archive. Old "skip for a
one-line tweak" narrows to "skip only for a pure wording fix".

**Proposer.** Forge already edits existing skills — that's the `fold` outcome. What it
lacked was a home for "skill Y is slightly wrong" when there's no new idea, only a
correction. `/notice` logs those and dead-ends; `/designit` is for specs. Revision 1
above was exactly this case and the old exclusion line told the operator to skip forge
for it — so the ceremony/competence line was drawn in the wrong place.

**Skeptic.**
- *Overlap* — none; no other skill revises skills.
- *Realness* — `docs/notice.md` is a standing queue of skill mis-calibrations; several
  lines per month. The exclusion was suppressing forge on its natural inputs.
- *Skill-fit* — forge is already the skill-management skill; this widens its mouth, not
  its identity.
- *Context cost* — a few lines in an already-loaded skill; no new `description`.
- Residual risk: prose-vs-path detection on the argument is a judgement call — step 2
  now names the branch explicitly so it isn't silently mis-read as a scan dir.

**Verdict.** Apply as a revision to `forge`. **Applied** (`SKILL.md` When-to-use,
step 2, argument-hint).

**Rating**: Recurrence 4 · Distinctness 5 · Skill-fit 5 · Scope tightness 3 (prose
detection is soft) · Context cost 5.
