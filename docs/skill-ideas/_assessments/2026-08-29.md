## 1. bug-echo

### Modeled skill

- **name** `bug-echo`
- **purpose** After a bug is fixed, characterize the defect as a *code pattern* and hunt
  the rest of the codebase for structural twins; rank each hit by confidence and blast
  radius. Report only — fix nothing.
- **triggers** `bug-echo`, `find the same bug elsewhere`, `where else does this happen`,
  `pattern-hunt after fix`, `siblings of this bug`
- **procedure** (1) characterize the just-fixed bug as the wrong *shape* (missing call,
  wrong arg form, absent guard), not the symptom; (2) derive search terms for that shape;
  (3) `Grep`/`Glob` for structurally similar sites; (4) read each hit — is it the same
  defect, or does local context save it; (5) rate each `confirmed` / `likely` /
  `needs-eyes` + blast radius; (6) present the ranked list.
- **outcome** an ad-hoc ranked list of sibling defect sites (no artifact, no pipeline
  status).
- **recurring need** a class bug rarely has one instance; ordinary review has no reason
  to connect file A's fix to file C's identical mistake.

### Proposer case

`devkit-api-change` exists precisely because one change breaks N consumers — the
"one mistake, many sites" phenomenon is already load-bearing in this setup.
`notice.md` repeatedly logs "same failure as an earlier note" (2026-08-09, 2026-08-28).
The idea file gives a concrete win (macOS dismiss button → 3 more sites). The procedure
is a clean characterize → grep → triage → rate loop with a crisp trigger ("just fixed X")
and a crisp outcome ("ranked sibling list"). An always-loaded description is two
sentences; the trigger is specific enough not to mis-fire; value on fire is high.

### Skeptic case

- **Overlap** — `code-review` shares the grep-read-rate discipline but takes a *diff or
  plan* and produces `review.md`; it does not fan out from a single just-applied fix into
  *unchanged* files. `devkit-api-change` shares the find-all-sites goal but is
  forward-looking call-site tracing of *one named symbol* in `src/devkit/`, not backward
  structural matching of a defect shape. `diagnose` finds one root cause and explicitly
  puts fixes out of scope. No true duplicate; real adjacency with two skills.
- **Realness** — "daily" is asserted with one anecdote. `notice.md` supports the *class*
  (repeated identical mistakes) but has no line about hand-hunting for siblings after a
  fix. Evidence is moderate, not strong.
- **Skill-shaped** — yes; repeatable procedure, not a preference or fact.
- **Context cost** — cheap description, specific trigger, high value on fire. Good ratio.

### Synthesis

Overlaps named: `code-review` (shared grep-read-rate discipline) and `devkit-api-change`
(shared find-all-sites goal). Per the Overlap check neither is a duplicate — different
input, different output, different method. Folding into `code-review` would mean adding a
"fan out from one fix" mode to a skill that is `disable-model-invocation`, opus-pinned,
artifact-producing and already near the size smell; it would blur its "review a diff
against a plan" identity. Distinctness ≥ 3, Skill-fit 5. Verdict: **add as new**, kind
`utility`, off the linear pipeline (a post-fix reflex, like `notice` is continuous).
Report-only, to stay clear of `resolve-review`.

### Rating

| Axis | Score | Justification |
|---|:-:|---|
| Recurrence | 3 | "Daily" claimed; one concrete anecdote; `notice.md` supports the class but not this exact gap. |
| Distinctness | 3 | Shares discipline with `code-review`, goal-family with `devkit-api-change`; no skill does post-fix structural fan-out. |
| Skill-fit | 5 | Clean characterize → grep → triage → rate loop; nothing memory-shaped. |
| Scope tightness | 4 | One trigger (just fixed a bug) → one outcome (ranked sibling list); slight fuzz in "same pattern". |
| Context cost | 4 | Cheap description, specific trigger, high value when it fires. |

## 2. prompter

### Modeled skill

- **name** `prompter`
- **purpose** Before acting on a prompt, judge whether a rewrite would materially improve
  the result; if so, show one tightened rewrite and wait for approval; stay silent when
  the prompt is already clear.
- **triggers** `prompter`, `is this prompt clear`, `rewrite my ask`, `check this before
  you run`
- **procedure** (1) parse the prompt for ambiguity — undefined scope, missing target,
  conflicting goals, no success criterion; (2) if it clears a bar, proceed silently; (3)
  else produce one rewrite naming scope/target/output; (4) present rewrite + the gaps it
  closes, wait; (5) act on the approved version.
- **outcome** a corrected prompt before a wasted turn (no artifact).
- **recurring need** a vague ask burns a full turn producing the wrong thing.

### Proposer case

`notice.md` 2026-08-02: "49 user interruptions and 11 compactions across 146 sessions,
concentrated where a bare nudge ('continue', 'implement') opened a multi-file task." The
pain is measured. A pre-flight prompt check catches exactly that. It stays quiet on clear
prompts, so the cost when not needed is near zero.

### Skeptic case

- **Overlap** — the highest-value slice of this (restate scope before running long on a
  bare nudge) was *already folded into `implement` and `plan-doc`* from that same
  `notice.md` line. `grill` already "pushes back before proceeding" (on reasoning, not
  prompt clarity); `designit` resolves ambiguity in a feature's shape. No single
  duplicate, but the discipline is already distributed.
- **Realness** — the pain is real, but a skill meant to fire "before the model acts on
  any prompt" is a change to *default behavior on every turn* — a `CLAUDE.md` / output-
  style concern, not a discretely-invoked procedure. The existing fix already targeted
  the high-risk case.
- **Skill-shaped** — weakly. "Evaluate every prompt, usually stay silent" is a standing
  disposition with no artifact and an "always" trigger. Skills that must self-invoke each
  turn are a poor fit — that is what global instructions are for.
- **Context cost** — an always-loaded description that says "checks whether your prompt
  needs a rewrite" invites mis-fire on every vague-sounding request; the honest
  implementation is a behavior change, not a skill call. Poor ratio.

### Synthesis

No hard single-skill overlap, but the discipline already exists: `notice.md` 2026-08-02
drove "restate scope before running long" into `implement` and `plan-doc`, which is the
best part of what `prompter` proposes. The general version fails Skill-fit — a standing
disposition, no artifact, "always" trigger; its home is `CLAUDE.md` / output style.
Skill-fit ≤ 2 → **drop**. The recurring case is covered; any broader "tighten a vague ask
before acting" belongs as a line in the user's global `CLAUDE.md`. The idea as written
("before the model acts", "stays quiet when fine") is the behavior-change framing, which
drops.

### Rating

| Axis | Score | Justification |
|---|:-:|---|
| Recurrence | 4 | Well-evidenced pain (interruption / compaction cluster on bare nudges). |
| Distinctness | 3 | No single duplicate; overlaps the scope-restate discipline already in `implement`/`plan-doc` and the `grill`/`designit` push-back family. |
| Skill-fit | 2 | Standing disposition, no artifact, "always" trigger; belongs in global instructions / output style. |
| Scope tightness | 2 | "Would this benefit from a rewrite" is a broad subjective bar; "stay quiet when fine" resists a crisp trigger. |
| Context cost | 2 | Always-loaded description encouraging per-turn second-guessing; honest form is a behavior change. |

## 3. skill-reviewer

### Modeled skill

- **name** `skill-reviewer`
- **purpose** Audit one existing `SKILL.md` against the authoring standard and report
  findings with `file:line` + severity, across lenses: safety, discoverability
  (including "why isn't it triggering"), architecture, tests.
- **triggers** `skill-reviewer`, `review this skill`, `why isn't my skill triggering`,
  `lint this skill`, `audit skill`
- **procedure** (1) read target `SKILL.md` + `skills/README.md` standard + constitution;
  (2) run each lens, cite `file:line`; (3) for a not-triggering complaint, compare
  description / trigger phrases against the failed request and against sibling skills for
  collision; (4) rate findings by severity; (5) report only.
- **outcome** a findings report on one skill.
- **recurring need** run before publishing a skill, or when one won't trigger and you
  can't tell why. As-needed, not daily (per the idea file).

### Proposer case

Meta-tooling is a real category here (`forge` just landed 08-29). Publishing a broken or
undiscoverable skill costs a silent no-fire that is hard to debug. The lenses are
concrete and the `file:line` + severity output matches this repo's review conventions.
Triggers are specific and unlikely to mis-fire.

### Skeptic case

- **Overlap** — `prune` step 5 *already* sweeps the registry flagging: orphan, stale
  `last-reviewed`, size smell, and Overlap-check collisions — the entire architecture /
  discoverability lens, on the same authoring standard, report-then-confirm. `forge`
  already carries the Overlap check + a 5-axis rating. Named overlaps: **`prune` step 5**
  (dominant) and **`forge`** (shared overlap-check + rating discipline).
- **Realness** — the idea file itself says "as-needed rather than daily". ~26 skills,
  authored in one burst; zero `notice.md` lines about skill-file review friction. The
  "why won't it fire" sub-use is real but narrow.
- **Skill-shaped** — yes, a clean multi-lens audit with an output.
- **Context cost** — an always-loaded description for a low-frequency meta-task already
  partly covered by `prune`. Marginal, helped a little by specific triggers.

### Synthesis

Two named overlaps. `prune` step 5 owns the biggest lens (size smell, overlap, orphan /
stale) across the registry; `forge` owns the overlap-check + rating discipline.
`skill-reviewer`'s distinct contribution is (a) *depth on one skill* rather than a sweep,
and (b) the **safety lens** (destructive `allowed-tools`, missing confirmations) plus the
**"why isn't this triggering"** diagnostic — neither `prune` nor `forge` does those. That
distinct core is real but thin, and the author calls the frequency low. Distinctness ≈ 2
(prune already owns the biggest lens), Recurrence ≈ 2. Rule: Distinctness ≤ 2 →
**fold into `prune`** (Recurrence is not ≥ 4, so the add-instead exception does not
apply).

**Fold** — add a single-skill deep-audit path to `prune`: when pointed at one
`skills/<name>/SKILL.md` rather than the whole registry, also check the **safety lens**
and, on a "doesn't fire" complaint, the **trigger-collision** check; report `file:line` +
severity; confirm before edits. Also widen `prune`'s trigger phrases. Exact Edit shown
below / on confirm.

| Distinctness | 2 | `prune` step 5 already runs the architecture / discoverability / overlap checks; unique part is the safety lens + trigger-collision diagnostic. |

## 4. unforget

### Modeled skill

- **name** `unforget`
- **purpose** One `UNFORGET.md` per project holding all deferred work — paused plans,
  mid-task spillover, audit findings, observed-but-unfixed bugs — each row rated
  (urgency, risk-of-fixing, risk-of-not-fixing, effort) and tagged to a release.
- **triggers** `unforget`, `what's blocking the release`, `add to unforget`, `what did we
  defer`, `log deferred work`
- **procedure** (1) capture — append a rated, release-tagged row with a source pointer;
  (2) query — filter by release / urgency, answer "what's blocking X"; (3) close — mark
  done with a commit pointer.
- **outcome** a single queryable deferred-work ledger per project.
- **recurring need** "what's blocking this release" today means walking TODO comments,
  plan files, and memory.

### Proposer case

`notice.md` is thick with deferral moments — plan steps found wrong mid-build, "step 6
not yet landed", tool-use interruptions leaving spillover, parked gates. The constitution
has a gate protocol for *one* parked decision but nothing aggregates deferred items
across a project. A rated, release-tagged ledger turns a manual sweep into one query.

### Skeptic case

- **Overlap** — the user's global instructions already route this: **erp-local
  `create_task`** is "a concrete follow-up that will not be done this session (a deferred
  fix, a discovered bug, a chore pushed to later)", and the "Where information goes" table
  says "Actionable and deferred → erp task." The constitution **gate protocol**
  (`specs/*/gates/*`, `awaiting-input → answered → consumed`) owns parked decisions.
  `code-review`'s `review.md` already has `Deferred` as a finding disposition, carried by
  `resolve-review`. Named overlaps: **erp `create_task`** (same purpose, existing store),
  **gate protocol**, **`review.md`**.
- **Realness** — the underlying deferral is real and frequent, but the *stores already
  exist*; the standing instruction is explicit: "Five stores. Put each fact in exactly
  one." A per-project `UNFORGET.md` would be a 6th, and it wouldn't even see the erp

- **Skill-shaped** — partly. The value is the *file convention*; the skill is thin glue,
  and it competes with an existing store rather than filling a gap.
- **Context cost** — an always-loaded description for a store that overlaps erp tasks and
  `review.md`, against an explicit "five stores" rule. Poor ratio; actively muddies where
  deferred work goes.

### Synthesis

Named overlaps: erp-local `create_task` (already the documented home for deferred
actionable work), the constitution gate protocol (parked decisions), and `review.md`
(deferred findings). `unforget` proposes a 6th per-project store in a setup whose
standing rule is "five stores, one fact one place". The genuinely missing piece is
*aggregation* — a single "what's blocking release N" view across gates + deferred
findings + erp tasks — but that is a query / report need, not a new ledger, and the
pieces live in different repos + an MCP store a local `UNFORGET.md` can't reach.
Distinctness ≤ 2 against `create_task` and Skill-fit ≤ 2 → **drop**. Deferred work keeps
routing to erp tasks / gates / `review.md`. If the aggregation pain is real, file a fresh

## 1. summary → modeled as `distill`

### Modeled skill

- **name** `distill`
- **purpose** Turn a body of material into judgment rather than coverage: first what a
  careful reader would notice that a skim would miss, then the three or four points to
  lead with. Anti-word-vomit by construction.
- **triggers** `distill`, `summarize this properly`, `what would I lead with`, `what does
  a skim miss`, `give me the presentation points` — `disable-model-invocation: true`, so
  it fires only when named.
- **procedure** (1) take the material in scope (a doc, a diff, a set of files, research
  output, this session); (2) **observation pass** — list only the non-obvious: what
  contradicts the headline, what the numbers imply but don't say, what is conspicuously
  absent, what a skim would read past; explicitly discard anything restating the surface;
  (3) **lead pass** — collapse that list into the 3–4 points you would actually open a
  presentation with, ranked by what changes the reader's decision; (4) each lead point is
  one line, claim-first, with its supporting observation beneath it; (5) name what was
  deliberately left out, in one line.
- **outcome** chat output: a short observation list plus 3–4 lead points. No artifact, no
  pipeline status, no file edited.
- **recurring need** default summarization is comprehensive-by-restatement — it re-covers
  the material at lower resolution instead of exercising judgment about what matters.

### Proposer case

The user has institutionalized anti-verbosity twice already — the global `CLAUDE.md`
communication-style block ("extremely concise, sacrifice grammar for concision") and the
active Concise output style. Both constrain *length*; neither supplies a *method* for
deciding what survives. That is exactly the gap this fills: the failure it targets is not
a long answer, it is a short answer that is still a flat restatement.

The two prompts in the idea file are not one instruction split in half — they are two
different operations, and the ordering is the whole trick. "What would a skim miss"
forces inference before selection; running lead-selection first yields the obvious
headline points, which is the word-vomit failure in compressed form. A skill is the right
container for a two-pass method the user currently retypes by hand each time.

Trigger→outcome is crisp: material in, 3–4 ranked lead points out. Nothing about it is
repo-specific, so it is portable `utility`, and as an explicit-invocation skill its
standing cost is a description line.

### Skeptic case

- **Overlap** — **`tldr`** is the real neighbour: both compress a document into a short
  top-of-mind form. **`grill`** ends with "the 2–3 weakest points that survived
  scrutiny", which is literally a lead-point selection. **`handoff`** compacts a session
  into what a fresh agent needs. **`teachme`** mines a session for what the user would
  otherwise miss. **`code-review`** / **`improve`** both terminate in a ranked findings
  list. "Produce the top N things that matter" is a *step in five existing skills* — a
  skill whose entire body is one widely-reused step is a suspicious shape.
- **Realness** — evidence is one idea file. `docs/notice.md` has no line about summary
  word-vomit, across 17 logged frictions. The concision instruments the user has already
  built (CLAUDE.md + output style) are evidence the *class* matters, but they equally
  support the reading that the need is already served and this adds a third instrument
  for the same complaint.
- **Skill-shaped** — thin. Stripped down, this is two prompts in sequence. There is no
  branch, no tool use, no artifact, no verification step, no state. Compare `bug-echo`
  (characterize → grep → read → rate) or `diagnose` (an evidence discipline with failure
  modes). "Ask A, then ask B" is closer to a saved prompt than a procedure — and this
  repo's `_processed/prompter.md` was dropped for adjacent reasons.
- **Context cost** — as a model-invocable skill the cost is bad: "summarize" is among the
  most common words in a request, the model summarizes constantly without being asked to,
  and a description advertising summarization would mis-fire on a large fraction of turns
  while adding nothing the model cannot already do.

### Synthesis

Every overlap the Skeptic named, addressed:

- **`tldr`** — fails the Overlap check on both limbs. Different input (arbitrary
  material, including a diff or a session, vs. exactly one `.md` file), different output
  (chat prose vs. an edited `## TLDR` section written back into that file), and
  incompatible methods: `tldr`'s governing rule is verbatim extraction of stated facts
  with "numbers, thresholds, timers, names: exact, never compressed" and a hard bar on
  touching the body. `distill` is interpretive — its first pass produces things the text
  does *not* say. Folding it into `tldr` would install a rule that contradicts `tldr`'s
  central one.
- **`grill`** — its verdict step selects lead points, but only over the answers produced
  by an adversarial interrogation it ran itself; it cannot be pointed at a document.
  Shared sub-step, not shared skill.
- **`handoff`** — different consumer (a fresh agent, not the user), different output (a
  brief on the MCP server), and its explicit brief is continuity: goal, state, decisions,
  next step. Non-obvious-observation mining is not in it.
- **`teachme`** — selects along the concept-gap axis and writes concept files; orthogonal.
- **`code-review` / `improve`** — ranked-findings tails over code they analysed
  themselves, artifact-producing, off-limits as hosts.

So the Skeptic's strongest point stands as a *shape* objection, not an overlap: the
top-N-selection step is common, but no skill takes arbitrary material as input and
produces lead-points as its output. Distinctness = 3, not ≤ 2 — the fold rule does not
fire.

On Skill-fit the Skeptic is half right and it costs the idea two points. This is a
two-pass method with a defined output contract, invoked on demand — that is more than a
preference and it is not memory-shaped, which is what separates it from the `prompter`
drop: `prompter` proposed evaluating *every* prompt (a standing disposition, "always"
trigger, behavior-change framing), whereas this fires only when the user asks for a
summary. But the Skeptic is right that the procedure is thin, so Skill-fit = 3, not 5.
Above the ≤ 2 drop bar.

The context-cost objection is decisive about *form*, not existence: this must be
`disable-model-invocation: true`, like `grill`, `handoff`, and `prune`. Explicit-only,
the mis-fire risk the Skeptic named goes to zero and the standing cost is one
description line.

Recurrence 4, Distinctness 3, Skill-fit 3 — no rule fires. Verdict: **add as new**, kind
`utility`, off the linear pipeline, explicit-invocation only. Flagged honestly as the
weakest `add` of the four ideas assessed today; if it does not get invoked within a
review cycle, `/prune` should drop it rather than let it sit.

### Rating

| Axis | Score | Justification |
|---|:-:|---|
| Recurrence | 4 | Summarizing is constant, and the user has built two separate anti-verbosity instruments (CLAUDE.md style block, Concise output style); against that, zero `notice.md` lines name this friction. |
| Distinctness | 3 | Real adjacency to `tldr` (compression) and `grill` (verdict step), but no skill takes arbitrary material in and returns lead-points out; both Overlap-check limbs fail against `tldr`. |
| Skill-fit | 3 | A two-pass method with a defined output contract and an explicit trigger — but no branching, tools, artifact, or verification; thin for a procedure. |
| Scope tightness | 4 | Crisp trigger→outcome (material in, 3–4 ranked lead points out); mild fuzz in what counts as "the material". |
| Context cost | 3 | Poor as model-invocable ("summarize" mis-fires broadly); cheap once pinned to `disable-model-invocation: true`. |

## 4. todo → erp task

### Modeled skill

- **name** `capture-todo`
- **purpose** Whenever work surfaces a follow-up that will not be done this session,
  write it to the erp tasker instead of leaving it in prose.
- **triggers** `todo`, `follow-up`, `we should later`, `deferred`
- **procedure** detect the deferred item → phrase it as one actionable task →
  `create_task` with project + due → confirm the id back.
- **outcome** an erp task row.
- **recurring need** every session ends with two or three "later" items that evaporate.

### Proposer case

The need is real and constant — this is the highest-recurrence item of the three, and
the cost of a lost follow-up is high (it resurfaces as a rediscovered bug). There is
prior art in the setup: `handoff` already exists to stop in-flight work evaporating, so
the *class* of problem is one this setup already spends a skill on.

### Skeptic case

- **Overlap** — direct duplicate of the `erp tasker` row in `CLAUDE.md`'s "Where
  information goes" table, which already reads: *"`create_task` for a concrete follow-up
  that will not be done this session."* The only delta the user is asking for is
  *scope*: today that table scopes erp to the home-infra domain; the request is to make
  it unconditional. That is a one-word edit to an existing rule, not a new skill.
- **Realness** — recurring, yes. Not disputed.
- **Skill-shaped** — no. There is no trigger→procedure→artifact arc a human would
  invoke. It is an always-on reflex that must fire *without* being called, which is
  exactly what a skill cannot guarantee: a skill only loads when its `description`
  matches. A rule in `CLAUDE.md` is in context unconditionally.
- **Context cost** — an always-loaded `description` buys nothing over the CLAUDE.md line
  that is already always loaded.

### Synthesis

The Skeptic's overlap finding is decisive and unanswered by the Proposer: the rule
exists, it is merely domain-scoped. Verdict **drop as a skill**; the content belongs in
`CLAUDE.md` "Where information goes", widening the erp row from home-infra to any
domain. `handoff` is not a counter-example — it produces an artifact on demand; this
does not.

**Rating** — Recurrence 5 (every session). Distinctness 1 (the rule is already written).
Skill-fit 1 (a reflex, not a procedure). Scope 4 (crisp trigger, crisp action).
Context cost 1 (pure duplication of always-loaded text).

## 5. durable fact → wiki, on user approval

### Modeled skill

- **name** `wikify`
- **purpose** When a session establishes a durable domain fact, propose a wiki doc or
  entity and write it once the user approves.
- **procedure** detect the durable fact → draft the doc → show it → on yes,
  `write_doc` / `append_to_doc` / `create_entity`.
- **outcome** a wiki doc.

### Proposer case

Stronger than idea 4 on one axis: it has a genuine human-in-the-loop step (draft, show,
await approval), which is more procedure-shaped than a bare `create_task`. Drafting a
good wiki doc — deciding doc vs entity, what to title it, what to leave out — is real
judgement that a written procedure could improve. `notice.md` shows the cost of *not*
having this: several 2026-08 entries are rediscoveries of facts an earlier session knew.

### Skeptic case

- **Overlap** — the `wiki` row of the `CLAUDE.md` table already specifies exactly what
  goes there ("durable domain knowledge a future session would waste time
  rediscovering") and which tools to use. Also brushes `distill` (compress material to
  what a skim misses) and `prune` (condense docs), though neither writes to wiki.
- **Realness** — recurring, but the *approval* framing weakens it: the user is asking to
  be asked, which is a consent policy, not a workflow.
- **Skill-shaped** — no, same failure as idea 4. Worse, actually: the trigger is
  "something durable was just established", which no `description` line can match
  reliably. If it only fires when invoked, it will not fire at the moment it matters.
- **Context cost** — same duplication.

### Synthesis

The Proposer's best point — that drafting the doc is real judgement — survives, but it
argues for *guidance*, not for a skill: the judgement is two or three sentences long and
fits inside the existing `CLAUDE.md` wiki row. The named overlap with that row is not
answered. Verdict **drop as a skill**; add to `CLAUDE.md`: at the point a durable domain
fact is established, propose the wiki write and get an explicit yes before writing.

**Rating** — Recurrence 4. Distinctness 1 (the table row covers it). Skill-fit 1 (a
consent policy). Scope 3 ("persistent data" is fuzzy at the edges). Context cost 1.

## 6. session-start cross-store recall

### Modeled skill

- **name** `recall` (or a widened `resume`)
- **purpose** Before starting substantive work, search brief / erp tasks / erp notes /
  wiki for prior context on this topic, present what was found, and let the user pick a
  thread or declare a fresh start.
- **triggers** `recall`, `what do we know about`, `any prior work on`, `resume`,
  `continue`, session start
- **procedure** derive 2-3 search terms from the opening request → query the four stores
  → dedupe and rank hits by recency and closeness → present a short numbered shortlist,
  each with store, title, date, one-line gist → user picks one or says fresh → on pick,
  read that item in full and restate the next action.
- **outcome** an oriented session (no file artifact).
- **recurring need** work restarts constantly across sessions; without this the model
  re-derives settled decisions, and `notice.md` 2026-08-02 shows a whole audit built on
  a wrong premise that prior context would have caught.

### Proposer case

Unlike ideas 4 and 5, this has a real multi-step procedure with judgement in it: term
derivation, cross-store dedupe, ranking, and a human decision point. It also has an
outcome that changes what happens next in the session. It is the one of the three that
a written procedure genuinely improves — "search four stores" done badly (one term,
literal match, no dedupe) returns nothing and trains the user to skip it.

### Skeptic case

- **Overlap** — heavy, with `resume`. `resume`'s procedure is: list candidates, pick by
  user hint or recency, read in full, follow its next step, restate before proceeding.
  Strip the word "brief" and that is *this* procedure line for line — well past the
  ~40% instruction-line threshold in the Overlap check, and it takes the same class of
  input and produces the same outcome (an oriented session). The only delta is the
  number of stores queried. Lighter brush with `handoff` (the write side) and `crawl`
  (orienting, but in-repo and artifact-producing — not a real overlap).
- **Realness** — strong. Not disputed.
- **Skill-shaped** — the *search* half is. The *"conversations start by"* half is not:
  a skill cannot guarantee it fires at session start. That needs a `SessionStart` hook
  in `settings.json` or a `CLAUDE.md` line — the skill is what the hook calls.
- **Context cost** — a second orientation skill sitting beside `resume` costs a second
  always-loaded `description` and forces a disambiguation the user should not have to
  make at session start.

### Synthesis

The Skeptic's `resume` overlap is the finding that decides this, and it is not waved
past — it is the reason the verdict is fold rather than add. The escape hatch in the
fold rule (Recurrence ≥ 4 *and* folding would push the host past ~120 lines) does not
apply: Recurrence is 5, but `resume` is ~15 lines and absorbs this comfortably.

Verdict **fold into `resume`**: widen it from brief-only to all four stores, add the
term-derivation and dedupe/rank steps, and add the explicit "or start fresh" branch so
an empty result is a clean outcome rather than a dead end. Keep the name — `resume` is
already the word the user reaches for at session start.

The Skeptic's second point stands alongside the fold: the trigger belongs in
`CLAUDE.md` (and/or a `SessionStart` hook), phrased as *run `/resume` before starting
substantive work on a known system*. Skill and trigger are separate changes; the fold
is worthless without the trigger.

**Rating** — Recurrence 5 (every session start). Distinctness 2 (`resume` already owns
this shape; only the store count differs). Skill-fit 4 (a real procedure with judgement
and a decision point; docked one because half the ask is a trigger, not a procedure).
Scope tightness 4 (crisp trigger→outcome; "related" is the only soft edge). Context
cost 3 (free if folded into `resume`; a new skill would rate 2).

### PS — fuzzy search on one MCP endpoint

Not a skill idea at all — it is a feature request against the erp/wiki MCP servers, and
a good one: the fold above is bottlenecked on four separate round-trips with literal
matching. Belongs in the erp tasker as a deferred task, not here. Note the dependency:
the folded `resume` works without it, just more slowly and with worse recall.
